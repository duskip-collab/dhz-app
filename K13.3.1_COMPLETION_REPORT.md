## 2. Implementovaná architektúra

### 2.1 Dvojvrstvový model
```
reports.core.ts (PURE)              → katalóg, gating (AND), agregácia   [unit-testovateľné]
        ▲
        │ importuje len typy + PERMISSIONS
members-overview.service.ts (SERVER) → getAuthContext → AND kontrola → RLS read
        ▲
        │ volá server službu (vlastná autorizácia)
reports/page.tsx (RSC)               → requirePermission(reports.view) → UI
```

### 2.2 Katalóg reportov (`getReportDefinitions()`)
Typované rozhranie `ReportDefinition` (bez `any`): `id`, `name`, `description`,
`module` (`ReportModule` union), `requiredPermissions: readonly Permission[]`, `status`.

| id | modul | requiredPermissions (AND) | status |
|---|---|---|---|
| `members-overview` | members | `reports.view` + `members.view` | **available** |
| `training-attendance` | training | `reports.view` + `training.view` | planned |
| `competitions-results` | competition | `reports.view` + `competition.view` | planned |
| `calendar-events` | calendar | `reports.view` + `calendar.view` | planned |
| `inventory-status` | inventory | `reports.view` + `inventory.view` | planned |
| `vehicles-inspections` | vehicle | `reports.view` + `inventory.view` | planned |
| `incidents` | incidents | `reports.view` + `incidents.view` | planned |
| `finance-accounts` | finance | `reports.view` + `finance.view` + `finance.export` | planned |
| `finance-cashflow` | finance | `reports.view` + `finance.view` + `finance.export` | planned |
| `finance-ledger` | finance | `reports.view` + `finance.view` + `finance.export` | planned |

**Invariant (test T2):** presne jeden report je `available` (`members-overview`);
finančné sú `planned`. Report sa neoznačí ako `available`, kým serverová vrstva nie je hotová.

### 2.3 Bezpečnostný model — logika AND (nie OR)
- `isReportAccessible()` používa `.every()` — používateľ musí mať **VŠETKY** oprávnenia.
  `reports.view` samotné **NESTAČÍ**; dátový report vyžaduje aj oprávnenie zdrojového modulu.
- **Nepoužité:** `requireAnyPermission` — jeho skutočná implementácia je OR, čo by
  bolo nebezpečné (udeľovalo by prístup na základe jediného oprávnenia). Zvolené
  `requirePermission(reports.view)` (jedno oprávnenie vstupu) + explicitná AND
  kontrola oprávnení zdroja v server službe.

### 2.4 Pilotný report — Prehľad členov (R1)
- **Zdroj:** tabuľka `members` (existujúca server služba pattern ako v `members.service.ts`).
- **Potrebné kľúče:** `reports.view` + `members.view`.
- **Ukazovatele:**
  - `total` = počet riadkov (všetky stavy),
  - `active` = `status='ACTIVE'`, `inactive` = ostatné,
  - `byMembershipType` = počet podľa `membership_type` (NULL → `UNKNOWN`).
- **Nulový výsledok:** `summarizeMembers([])` vráti `{total:0, active:0, inactive:0, byMembershipType:{}}` — bez chyby; UI zobrazí „Zatiaľ nie sú evidovaní žiadni členovia."
- **Minimalizácia dát:** `SELECT` len stĺpcov `membership_type, status` (žiadne PII, žiadne financie).

Defense-in-depth server služby:
1. `getAuthContext()` — neprihlásený → redirect `/login`.
2. AND kontrola `ctx.permissions` — chýba ktorékoľvek oprávnenie → `AuthError 403`.
3. Potvrdenie cez server RPC `has_permission` pre **obe** oprávnenia.
4. RLS na `members` — bez `members.view` žiadne riadky (posledná línia).

> RLS nie je obchádzaná: čítanie ide cez štandardný serverový Supabase klient
> (`createClient()` z `@/lib/supabase/server`), nie service-role.
