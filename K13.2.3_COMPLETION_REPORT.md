## 2. Zistenia a opravy

### F1 — HIGH · `"use server"` exportoval ne-async hodnoty (build/runtime breaker)

**Dôkaz:** `attachment-actions.ts` mal `"use server"` na riadku 1 a exportoval
`ATTACHMENT_BUCKET` (string), `MAX_ATTACHMENT_BYTES` (number) a
`ALLOWED_ATTACHMENT_TYPES` (Set). Overené v next@16.4.0:
`node_modules/next/dist/build/webpack/loaders/next-flight-loader/action-validate.js`

```js
if (typeof action !== 'function') {
  throw new Error(`A "use server" file can only export async functions, found ${typeof action}.`)
}
```

Klient (`AttachmentManager.tsx`) tieto konštanty importoval priamo z action
modulu → build/runtime by hodil výnimku.

**OPRAVA:** konštanty + čisté validačné funkcie presunuté do nového
`src/app/dashboard/finance/attachment-constants.ts` (žiadny `next/*` import,
teda priamo unit-testovateľné). `attachment-actions.ts` exportuje **výhradne**
`async function` + `type` (overené: 4 async funkcie + 1 typ). Klient importuje
konštanty z nového modulu. Re-export z action modulu bol zámerne
**nepridaný** — opakovala by sa tá istá chyba.

### F2 — HIGH · Žiadna kontrola oprávnení v žiadnej akcii

**Dôkaz:** pôvodné `loadTransactionAttachments`,
`uploadTransactionAttachment`, `deleteTransactionAttachment`,
`getAttachmentDownloadUrl` nikdy volali `getAuthContext()` ani
`has_permission`. RLS existovalo (`finance.view` / `finance.create` /
`finance.edit`), no aplikačná vrstva túto kontrolu neurobila — nešlo
rozlíšiť „neexistuje“ od „nemáte oprávnenie“ a chýbala defence-in-depth.

**OPRAVA:** pridaný `requirePermission(permission)`, ktorý používa
**existujúci** `getAuthContext()` a **existujúci** katalóg
(`PERMISSIONS.FINANCE_VIEW / FINANCE_CREATE / FINANCE_EDIT`). Mapovanie:

| Akcia | Oprávnenie | Zhoda s RLS |
|---|---|---|
| `loadTransactionAttachments` | `finance.view` | `finance_attach_select` (20261015) |
| `uploadTransactionAttachment` | `finance.create` | `finance_attach_insert` + Storage INSERT |
| `deleteTransactionAttachment` | `finance.edit` | `finance_attach_delete` + Storage DELETE |
| `getAttachmentDownloadUrl` | `finance.view` | Storage SELECT / `can_read_finance_attachment` |

**Nevytvorené** žiadne nové oprávnenia. `finance.post` ani `finance.void`
v katalógu (**overené** v `src/lib/auth/permissions.ts`) **neexistujú** a
neboli ani vymyslené — posting/void sa naďalej rieši výhradne cez
`finance.edit` v `finance_guard_transactions()`.

### F4 — HIGH · Validácia typu súboru len podľa `File.type`

**Dôvod:** `:183` `ALLOWED_ATTACHMENT_TYPES.has(file.type)` — `File.type` je
**klientsky údaj**, ktorý útočník nastaví ľubovoľne. Súbor `.pdf` s obsahom
HTML/exe by prešiel.

**OPRAVA:** serverová validácia v 4 krokoch, **nie** na základe `File.type`:

1. veľkosť (`> 0` a `<= MAX_ATTACHMENT_BYTES`), overená aj na skutočných bajtoch;
2. **magic bytes** (`detectAttachmentMime`) — `%PDF-`, PNG signature,
   `RIFF....WEBP`, JPEG `FF D8 FF`;
3. **allow-list prípon** (`ALLOWED_ATTACHMENT_EXTENSIONS`) — musí sedieť s obsahom;
4. deklarovaný `File.type` (ak je) musí sedieť s detekovaným obsahom.


### F5 — HIGH · `uploaded_by` sa dal podvrhhnúť / bol NULL

**Dôkaz:**
* insert v `uploadTransactionAttachment` `uploaded_by` **nenastavoval**;
* jediný guard trigger `finance_guard_transactions()` (migrácia 20261015) je
  napojený **iba** na `finance_transactions`;
* RLS `finance_attach_insert` požaduje len `finance.create` — klient tak mohol
  cez priamy PostgREST zápis nastaviť `uploaded_by` na cudziu identitu.

**OPRAVA (dvojvrstvová):**
1. Server action teraz posiela `uploaded_by: auth.userId` z overenej identity.
2. **NOVÁ migrácia** `20261020_finance_attachments_guard.sql` —
   `BEFORE INSERT OR UPDATE OR DELETE` trigger `finance_guard_attachments()`,
   ktorý pri existujúcom `auth.uid()` **vždy prepíše** `NEW.uploaded_by`.
   Kontexty bez `auth.uid()` (service_role, migrácie) si držia zadanú hodnotu —
   rovnaký princíp ako v existujúcom `finance_guard_transactions()`.

### F6 — MEDIUM · Delete mazal metadácie pred objektom → neviditeľná sirota

**Dôkaz:** pôvodné poradie bolo `DELETE metadata` → `Storage.remove()`. Pri
zlyhaní `remove()` zostal objekt v Storage **bez metadát** — teda neviditeľný
a nezáznamný.

**OPRAVA:** poradie obrátené na **objekt → metadácie**. Pri zlyhaní mazania
metadát vznikne „mrtvy“ riadok, ktorý je **viditeľný** a používateľ môže akciu
opakovať. Delete metadát je navyse vedený aj podľa `transaction_id` **a**
`storage_path`, aby sa nemazal iný riadok.

**Dôkaz:** `getAttachmentDownloadUrl` nekontroloval `finance.view`,
neoveroval väzbu cesty a nevytváral druhú vrstvu IDOR ochrany.

### F8 — MEDIUM · `transactionId` nebol validovaný ako UUID

**Dôkaz:** `:116` `` `${transactionId}/${Date.now()}-${safe}` `` — hodnota

**OPRAVA:** `isUuid()` gate v `upload`, `load`, `delete`, `download`;
`buildAttachmentPath()` navyše **vyhadzuje výnimku**, ak by výsledná cesta

### F9 — LOW · `sanitizeFileName` povolil `..` segmenty

**Dôkaz:** pôvodná verzia neodstrihovala úvodné/koncové `.` `-` `_`, takže

`displayFileName()` odstraňuje C0/C1 control znaky a DEL (explicitne cez code
points). Pokryté testami.

## 5. Konzistencia operácií

| Situácia | Správanie |
|---|---|
| Upload OK, insert metadát zlyhá | **Kompenzácia:** `Storage.remove([path])` okamžite; ak zlyhá aj to, loguje sa serverovo (orphan). |
| Delete objektu OK, delete metadát zlyhá | Vráti sa **chyba** (nie falošný úspech); riadok zostáva **viditeľný**, akciu možno opakovať. |
| Objekt už neexistuje pri delete | Storage vráti chybu → akcia vráti chybu; používateľ môže opakovať. Nie je to maskované ako úspech. |
| Opakovaná požiadavka (upload) | `upsert: false` + unikátny `Date.now()` prefix → nový objekt, žiadne tiché prepísanie. |
| Opakovaná požiadavka (delete) | `isUuid` gate + `.single()` → druhá požiadavka vráti „Priloha sa nenasla.“ |
| Zmena stavu transakcie počas operácie | DRAFT gate sa overuje **serverovo pred každým zápisom**; DB guard ho overuje znova v `BEFORE` triggeri. |
| Súbežné uploady | Unikátna cesta (`Date.now()`), `upsert: false` → bez kolízie; RLS + guard platia riadok po riadku. |
| Súbežné mazania | Delete vedený podľa `id` + `transaction_id` + `storage_path`; druhé mazanie nenájde riadok. |

**HRANICA ATOMICITY (explicitne zdokumentovaná, netvrdíme jednu transakciu):**
PostgreSQL a Supabase Storage **nie sú** v jednej transakcii. Upload objektu
a zápis metadát (a rovnako delete) sú **dve samostatné operácie**. Nie je možné
garantovať atómicosť. Rieši sa to **kompenzačnými operáciami** a **poradím**
(výberom menej škodlivej poruchy), čo je popísané vyššie a v komentároch kódu.
