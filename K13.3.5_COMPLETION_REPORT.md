## 2. Implementovaná architektúra

Rovnaký vzor ako K13.3.1–K13.3.4 (defense-in-depth, žiadny service-role):

1. **Stránka** (`page.tsx`, server component):
   - `requirePermission(PERMISSIONS.REPORTS_VIEW)` ako **prvý** krok — pred
     akýmkoľvek čítaním dát; neprihlásený/neoprávnený = existujúce správanie guardu.
   - AND gating z katalógu cez `isReportAccessible()` (`reports.view` A `finance.view`);
     bez `finance.view` sa dáta vôbec nečítajú (len karta „Report nie je dostupný").
2. **Služba** (`finance-monthly-summary.service.ts`):
   - `authorizeFinanceMonthly()`: `getAuthContext()` → filter chýbajúcich oprávnení
     (AND) → potvrdenie **každého** oprávnenia cez server RPC `hasPermissionServer`
     (druhá línia obrany).
   - Čítanie cez štandardný SSR `createClient()` (RLS rešpektovaná; **0** výskytov
     `service_role` v reportoch — overené staticky).
   - Jeden SELECT `finance_transactions` (`type, status, amount_minor,
     transaction_date, category_id`, `.eq("status","POSTED")`) + jeden SELECT
     `finance_categories` (`id, name, direction, sort_order`). Obe tabuľky má pod
     RLS `finance.view`.
3. **Agregácia** (`reports.core.ts`, čistá funkcia `summarizeFinanceMonthly()`):
   unit-testovaná bez IO.
4. **UI**: `Card`/`Badge`/`Button` (existujúci dizajnový systém), spätný odkaz na
   `/reports`. Žiadna paralelná navigácia.

## 3. Pilotný ekvivalent: `finance-monthly-summary`

- **Zdrojové dáta**: `finance_transactions` (len `status='POSTED'`) +
  `finance_categories` (názvy/smer). **Žiadny** pohľad `v_finance_monthly_*`
  v schéme neexistuje (overené v `database.types.ts`) — agregácia je aplikačná.
- **Ukazovatele**: mesačne (`transaction_date` → `YYYY-MM`) príjmy
  (`INCOME`), výdavky (`EXPENSE`), netto = príjmy − výdavky, počet POSTED
  transakcií, počet transferov (evidenčne). Kumulatívne totály za obdobie.
  + analýza kategórií (POSTED INCOME/EXPENSE podľa `category_id`).
- **Finančné invarianty**:
  - do súčtov idú **výhradne** riadky `status='POSTED'` (DRAFT/VOID ignorované
    — dokonca dvakrát: `.eq("status","POSTED")` v dotaze **a** filter v čistej funkcii);
  - `TRANSFER_IN`/`TRANSFER_OUT` sú **cash-flow neutrálne** — nikdy do
    príjmov/výdavkov, len `transferCount` (potvrdzuje K13.3.0 §7.2);
  - sumy zostávajú v minor units; EUR zobrazenie je výhradne prezentačná vrstva (`eur()`).
- **Prázdny výsledok**: `months=[]`, totály nulové; UI zobrazí „Zatiaľ nie sú
  evidované žiadne zaúčtované (POSTED) transakcie." — bez chyby.

## 6. Otvorené riziká a závislosti

- **RLS vs. server (identity)**: `has_permission` RPC aj RLS sú overené len
  staticky; runtime overenie na DEV DB zostáva **BLOCKED** (T-body z K13.3.0 §5.4).
- **`transferCount` vs. saldá**: report ukazuje transfery len evidenčne; saldá
  účtov (report `finance-accounts`) sú stále `planned` a závisia na
  `finance_account_balances` (odvodený pohľad).
- **Nezmenené**: `finance-accounts` a `finance-cashflow` ostávajú `planned`
  (K13.3.6+); export financií (`reports.export` + `finance.export` + audit) je
  mimo rozsahu; otvorená závislosť `vehicle.view` vs `inventory.view` z K13.3.0
  zostáva **nezmenená** (report vozidiel ju obchádza serverovým gatingom, nie opravou).
- **Výkon**: jeden SELECT na transakcie bez dolného/horného filtra dátumu — pri
  veľkom objeme dát zvážiť filter obdobia (index
  `idx_finance_tx_transaction_date` existuje; je to budúci krok).
