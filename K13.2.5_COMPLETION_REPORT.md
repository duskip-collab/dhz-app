## 1. Analysis (pre-change behavior)

`v_uid := auth.uid()`; `has_permission(NULL, …)` is always false.

- `20261015` (original):
  - INSERT DRAFT: allowed; `created_by`/`updated_by` forced only if `v_uid IS NOT NULL`.
  - INSERT POSTED: requires `finance.edit` (no NULL carve-out → NULL identity always blocked).
  - POSTED row: non-VOID UPDATE rejected unconditionally; `POSTED → VOID` requires `finance.edit`; amount/account/type/date/transfer immutable.
  - VOID row: always immutable.
  - `DRAFT → POSTED`: requires `finance.edit`; stamps `posted_at`/`posted_by` only if identity exists.
  - `DRAFT → VOID`: requires `finance.edit`.
  - DELETE: only DRAFT allowed.
- `20261022_finance_transactions_guard_fix.sql` (K13.2.4):
  - Added `v_uid IS NOT NULL AND` to all 4 `finance.edit` checks (direct POSTED INSERT, `POSTED → VOID`, `DRAFT → POSTED`, `DRAFT → VOID`).
  - Effect: any request where `auth.uid() IS NULL` **bypassed the posting authorization entirely**; NULL identity became implicitly trustworthy.

## 2. Behavior change (this migration)

File: `dhz-app/supabase/migrations/20261022_finance_transaction_guard_fix.sql` (`CREATE OR REPLACE`; `20261015` untouched).

- `auth.uid() IS NOT NULL`: unchanged — all 4 checks still require `finance.edit`.
- `auth.uid() IS NULL`:
  - Direct POSTED INSERT, `POSTED → VOID`, `DRAFT → POSTED`, `DRAFT → VOID`: **rejected (`P0001`) unless `app.finance_pti_enabled = 'on'`**.
  - DRAFT INSERT, VOID immutability, POSTED-field immutability, DELETE-only-DRAFT: unchanged.
- Trust boundary: session GUC `app.finance_pti_enabled`, set only via `public.finance_pti_enable()` (SECURITY DEFINER; `session_user` must be `service_role`/`postgres`; EXECUTE granted to `service_role` only). No new permission/role.
- Audit/`created_by`/`updated_by`/`posted_by` behavior preserved.
- NULL-safety: guards use `current_setting('app.finance_pti_enabled', true) IS DISTINCT FROM 'on'`, so an **unset** GUC can never authorize — no unverified exception.
