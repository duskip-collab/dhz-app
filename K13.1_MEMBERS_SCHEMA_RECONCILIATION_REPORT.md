# K13.1 — Members Schema Reconciliation & Security Review

## Zhrnutie rozhodnutia

- Jediný checked-in DDL, ktorý vytvára členskú schému, je `20261006_core_database.sql`.
- [K13.3.0_ARCHITECTURE_REPORT.md](./K13.3.0_ARCHITECTURE_REPORT.md) výslovne dokumentuje tento core model ako overený zdroj a uvádza `member_type` + `youth_category` ako zamýšľané vyjadrenie typu členstva.
- [database.types.ts](./src/types/database.types.ts), [members.service.ts](./src/lib/members/members.service.ts), validácia a UI používajú odlišný model vrátane `membership_type`, `member_number` a `member_guardians`. Pre tieto zmeny neexistuje checked-in migrácia.
- Preto je **DB baseline v repozitári jednoznačný, ale schválený cieľ pre aktuálnu K8 aplikačnú schému nie je jednoznačný**. Pracovná hypotéza má byť core migrácia ako DB source of truth; nie je však bezpečné prepísať službu/UI ani vytvoriť evolučnú migráciu bez rozhodnutia, či K8 model je schválený a nasadený inde.
- Zmeny členskej schémy ani RLS neboli vykonané. Tento dokument je analýza a plán.

V [supabase/migrations/20261006_core_database.sql](./supabase/migrations/20261006_core_database.sql):

- `id uuid primary key default gen_random_uuid()`
- `profile_id uuid unique references public.profiles(id) on delete set null`

## 2. Návrh kanonického dátového modelu

### Odporúčaný baseline — zachovať core identitu a existujúce väzby

Kanonický záznam člena má zachovať `public.members.id` ako trvalý PK a väzby ostatných modulov. Model pre dospelých a mládež možno vyjadriť bez novej tabuľky:

| Doménová kategória | `member_type` | `youth_category` |
|---|---|---|
| Dospelý | `adult` | `NULL` |
| Mládež bez špecifickej kategórie | `youth` | `NULL` |
| Prípravka | `youth` | `preparatory` |
| Dorast | `youth` | `dorast` |

Aktívny/neaktívny stav je `member_status` (`active` / `inactive`). Login používateľa sa pripája voliteľne cez `profile_id`. Zákonní zástupcovia sú v `guardians`, naviazaní cez `member_id`, s rozdeleným menom a vlastnými kontaktnými údajmi.

Tento model je priamo doložený DDL a zodpovedá požiadavkám na členstvo, status, voliteľný profil, kontakty, narodenie a guardian väzby. Nie je však potvrdené, či chce produkt vyžadovať `member_number` alebo evidovať ďalšie K8 polia.

### Aplikačné požiadavky, ktoré ešte nie sú schválené DB kontraktom

Tieto polia/tvary sa používajú v UI/service, ale nie sú doložené core DDL:

- `member_number`: povinný vo formulári. Nie je možné ho bezpečne doplniť z existujúceho poľa; zdroj a unikátnosť vyžadujú rozhodnutie.
- `title` vs `position`: nie sú automaticky ekvivalentné.
- `birth_date` ↔ `date_of_birth`: semanticky priamy kandidát na rename/backfill.
- `membership_type` ↔ dvojica `member_type` + `youth_category`: mapovanie je možné, ale `YOUTH` bez kategórie treba zachovať.
- `status` uppercase ↔ lowercase: mechanické mapovanie `ACTIVE → active`, `INACTIVE → inactive` je možné po runtime potvrdení enumu.
- `left_at`: core model ho nemá; automatické odvodenie z dátumu poslednej zmeny by bolo nesprávne.
- `notes` vs `internal_note`: treba potvrdiť citlivosť a rozsah viditeľnosti.
- `photo_path` vs `photo_url`: cesta v private Storage nie je zameniteľná s verejnou/absolútnou URL.
- `created_by` / `updated_by`: nemajú zdrojové hodnoty v baseline.
- `auth_user_id` vs `profile_id`: `profile_id` už vedie na profil naviazaný na `auth.users`; pred rename je potrebné potvrdiť cardinalitu a správanie pri odpojení účtu.
- `member_guardians` vs `guardians`: názov, sploštené meno, `user_id`, `is_primary_contact` a audit polia nemajú v core modeli priame ekvivalenty. Core tabuľka navyše uchováva adresu, ktorú K8 model nemá.

**Neschválené návrhy:** nepridávať `member_number`, `left_at`, `member_guardians`, `user_id` ani audit stĺpce iba preto, aby prešli typy. Najprv potvrdiť ich produktovú potrebu.

## 5. Samostatný RLS bezpečnostný audit

### Aktuálny stav podľa core migrácie

`public.members` má RLS enabled, ale SELECT policy je:

```sql
create policy members_select_authenticated
on public.members for select to authenticated
using (true);
```

Tá istá migrácia dáva `GRANT SELECT ON public.members TO authenticated`. Výsledok: **priame Supabase API SELECT pre ľubovoľného prihláseného používateľa vráti všetky riadky, ktoré táto policy nezablokuje — a táto policy nefiltruje žiadny riadok.** `members.view` kontrola v `members.service.ts` chráni iba volania, ktoré prechádzajú cez túto serverovú službu; nie priame PostgREST SELECT volania používateľa s authenticated JWT. Tvrdenie architektúrneho reportu „RLS čítanie: members.view“ nezodpovedá SQL politike.

Rovnaký vzor `USING (true)` + authenticated SELECT grant je v core migrácii aj pre `guardians`, ktoré obsahujú telefóny, emaily a adresu zákonných zástupcov.

### Roly a člen permissions

Core seed priraďuje `members.view` rolám `ADMIN`, `VEDENIE`, `VELITEL`, `POKLADNIK`, `TRENER` a `CLEN`. `RODIC` (`RODIC`) ho v tomto seed bloku nemá. Z toho vyplýva, že jednoduchá permission-based SELECT politika by zodpovedala väčšine interných rolí, ale blokovala by rodičov.

V core guardian modeli nie je guardian priamo prepojený s `auth.users`/`profiles`; preto neexistuje dôkazný kľúč na bezpečné obmedzenie rodiča iba na vlastné dieťa. K8 `member_guardians.user_id` by také prepojenie naznačovalo, ale jeho tabuľka/migrácia chýba. Nesmie sa automaticky predpokladať ani zaviesť bez schválenia.

### Minimálny návrh politiky — podmienený rozhodnutím

Ak rozhodnutie znie, že celý register je čitateľný pre používateľov s `members.view` a rodičia nemajú prístup k členským riadkom, nahradiť members SELECT policy (v doprednej migration) takto:

```sql
drop policy if exists members_select_authenticated on public.members;
create policy members_select_authenticated
on public.members for select to authenticated
using (public.has_permission((select auth.uid()), 'members.view'));
```

Toto používa existujúci `public.has_permission(uuid,text)`:

- je `SECURITY DEFINER`, `STABLE`;
- má pevný `search_path = public`;
- query v tele kvalifikuje objekty ako `public.user_roles`, `public.roles`, `public.user_permissions`, `public.permissions`, `public.role_permissions`;
- má `EXECUTE` grant pre `authenticated`;
- policy odovzdá výhradne `(select auth.uid())`, nie caller-supplied user id.

Tým helper vyhodnotí oprávnenie bez re-enterovania RLS na tabuľkách rolí. Meniť túto policy bez odpovede pre rolu `RODIC` môže odobrať existujúcu aplikáciou implicitne povolenú funkcionalitu. Guardian policy musí byť riešená samostatne s rozhodnutím o vlastnom dieťati a väzbe guardian↔auth user; jednoduché `members.view` môže odhaliť osobné kontaktné údaje zákonných zástupcov príliš širokej skupine.

### Write pravidlá (zistené, nemenili sa)

- `members_insert_admin`: iba `ADMIN`, `VEDENIE`, `VELITEL`.
- `members_update_admin`: rovnaké roly.
- `members_delete_admin`: iba `ADMIN`.
- Guardian insert/update: `ADMIN`, `VEDENIE`, `VELITEL`, `TRENER`; delete iba `ADMIN`.
- Tabuľkové write GRANTy sú pre authenticated, ale RLS write policies ďalej filtrujú.
- [20261023_auth_rls_recursion_fix.sql](./supabase/migrations/20261023_auth_rls_recursion_fix.sql) používa `has_role` pre auth metadata manage policies; `members` policies však majú svoje inline role joins. Podľa aktuálnych SELECT policies na `user_roles` a `roles` sa tieto joins čítajú cez authenticated SELECT policies; runtime rekurzia nebola overená.

5. Potvrdiť, či `members.view` má byť enforced aj v RLS, nie iba server service; skontrolovať rovnakú expozíciu kontaktných údajov cez guardians.
6. Poskytnúť read-only snapshot alebo prístup k autorizovanej DEV DB na potvrdenie deployed schema a RLS.

## Záver

**Implementácia schémy ani RLS opravy nie je pripravená. Vyžaduje rozhodnutie o cieľovej schéme a prístupe rodičov, plus runtime snapshot autorizovanej DB.** Checked-in core migration je jediný preukázaný DB baseline; nepreukazuje však, že aktuálna DEV/PROD DB ho stále používa.
