## 1. ZHRNUTIE PROBLÉMU

V `dhz-app/supabase/migrations/` existujú **dve migrácie s rovnakou časovou značkou `20261022`**,
ktoré obe obsahujú `CREATE OR REPLACE FUNCTION public.finance_guard_transactions()`:

| Súbor | Kľúč | Semantika pri `auth.uid() IS NULL` |
|---|---|---|
| `20261022_finance_transactions_guard_fix.sql` | **K13.2.4** | ku všetkým 4 kontrolám `finance.edit` pridá `v_uid IS NOT NULL AND` → **NULL identita kontroly preskočí** |
| `20261022_finance_transaction_guard_fix.sql` | **K13.2.5** | podmienku `v_uid IS NOT NULL` **odstraňuje** a namiesto nej vyžaduje explicitný GUC `app.finance_pti_enabled = 'on'` (hranica dôvery) |

Oba súbory sú navzájom **opačné** v bezpečnostnej invariante „chýbajúca identita nesmie
automaticky znamenať preskočenie autorizácie". K13.2.5 navyše obsahuje **syntaktickú chybu**
(chýbajúci `END IF;` — pozri §4.2), takže jej aplikácia zrejme zlyhá už pri `CREATE FUNCTION`.

**Tri nezávislé blokátory (všetky staticky preukázané, runtime BLOCKED):**

1. **P0 — Konflikt poradia:** pri lexikografickom radení názvov sa K13.2.5 (hardening) aplikuje
   **PRVÁ** a K13.2.4 (obchádzačka) **DRUHÁ** → na čistej DB by poslednou platnou definíciou
   bola verzia, ktorá **obchádza `finance.edit` pri NULL identite**.
2. **P0 — Syntaktická chyba v K13.2.5:** `IF` z bloku `DRAFT -> POSTED` (riadok 155) nemá
   uzatvárací `END IF;` → plpgsql parser by pri `CREATE OR REPLACE FUNCTION` hlásil chybu →
   migrácia by pri `db push` **zlyhala** a blokovala by všetky nasledujúce migrácie.
3. **P0 — Duplicitná verzia v migračnom ledgere:** obe súbory majú podľa vzorca CLI
   `^([0-9]+)_(.*)\.sql$` **rovnakú verziu `20261022`**, ale tabuľka
   `supabase_migrations.schema_migrations` má `version text ... PRIMARY KEY` → dva riadky
   s rovnakou verziou tam nemôžu byť; konvergenčné správanie `db push` je neisté.

**Stav produkcie: NO-GO** (potvrdzuje záver K13.4.4). Táto fáza problém iba overila a
pripravila návrh opravy — **nič nebolo aplikované**.

### 4.2 NOVÝ NÁLEZ — syntaktická chyba v K13.2.5 (blokuje akékoľvek `db push`)

Štruktúrna stopa `IF` / `END IF` v `20261022_finance_transaction_guard_fix.sql`
(počítanie regexom `^\s*IF\b` vs `^\s*END IF;` + manuálna LIFO stopa blokov):

```
155: IF OLD.status = 'DRAFT' AND NEW.status = 'POSTED' THEN      ← blok OTVORENÝ
156:     IF v_uid IS NOT NULL THEN … 163: END IF;                (uzavreté)
165:     IF v_uid IS NOT NULL THEN … 167: END IF;                (uzavreté)
       ← !!! TU CHÝBA „END IF;" pre blok z riadku 155 !!!
168:     -- DRAFT -> VOID: require finance.edit …
169:     IF OLD.status = 'DRAFT' AND NEW.status = 'VOID' THEN … 178: END IF;
180:     RETURN NEW;
181: END IF;        ← v skutočnosti zatvára blok 155, nie „IF TG_OP='UPDATE'" (117)
193: END;           ← blok 117 stále otvorený → SYNTAX ERROR
```

- Počty: **K13.2.5 → 24 `IF` / 23 `END IF`**; K13.2.4 → 19/19; baseline `20261015_finance_module.sql` → 41/41.
  Kontrola variantov `END  IF` / `ENDIF` / `END IF` bez `;` → žiadne (t.j. chýbajúci `END IF;`
  nie je zapísaný iným štýlom).
- `check_function_bodies` má v PostgreSQL predvolenú hodnotu `on` → plpgsql validator **parsuje
  telo už pri `CREATE OR REPLACE FUNCTION`** → predikcia: migrácia K13.2.5 **zlyhá pri
  aplikácii** (SQLSTATE triedy 42601/42P17 — „syntax error / unterminated IF").
- Dôsledok reťazca: pri lexikografickom poradí (K13.2.5 je PRVÁ) by `db push` **zlyhal na
  prvej z dvoch 20261022 migrácií** a **nedosiahol by** žiadnu opravnú migráciu s vyššou
  časovou značkou (napr. navrhovanú `20261025…`). Aj v opačnom poradí by `db push` zlyhal
  na K13.2.5 po aplikácii K13.2.4 → stav ledgeru = „neúspešná push", DB = K13.2.4 definícia.
- Rozsah: chyba je **len v tomto súbore** — K13.2.4 aj `20261015` sú štruktúrne vyvážené.
- Overenie: **STATICKY OVERENÉ** (počty + LIFO stopa). **RUNTIME OVERENÉ NIE** — proti DB
  nebolo spustené (zákaz fázy); finálne potvrdenie vyžaduje autorizované DEV prostredie.

## 5. BEZPEČNOSTNÁ ANALÝZA `auth.uid()` A `finance.edit` (KROK 4 — POŽADOVANÁ INVARIANTA)

### 5.1 Základné fakty

- `public.has_permission(p_user_id uuid, p_permission_code text)` — `20261006_core_database.sql:321-351`,
  `LANGUAGE sql STABLE SECURITY DEFINER SET search_path = public`; tri `EXISTS` poddotazy porovnávajú
  `ur.user_id = p_user_id` / `up.user_id = p_user_id` → pri `p_user_id IS NULL` je výsledok
  **vždy `false`** (`NULL = NULL` nie je pravdivé). Grant: `authenticated, service_role` (riadok 843).
- `auth.uid()` v triggeri: `v_uid uuid := auth.uid();` — obe definície sa zhodujú.
- Permission key `finance.edit` **existuje** (`src/lib/auth/permissions.ts:28 FINANCE_EDIT`);
  kľúče `finance.post` / `finance.void` **neexistujú** a **neboli vymýšľané** (overené v
  `src/lib/auth/permissions.ts` — finance.view/create/edit/export/manage_access).

### 5.2 Správanie oboch variantov

| Situácia | K13.2.4 (obchádzačka) | K13.2.5 (GUC hranica) |
|---|---|---|
| `v_uid` existuje, má `finance.edit` | povolené (obe rovnako) | povolené (obe rovnako) |
| `v_uid` existuje, `finance.edit` NEMÁ | **odmietnuté P0001** (obe rovnako) | **odmietnuté P0001** (obe rovnako) |
| `v_uid IS NULL` (bez GUC) | **kontroly preskočené → POVOLENÉ** ❌ porušuje invarianu 1 a 2 | **odmietnuté P0001** ✅ (`current_setting(...,true) IS DISTINCT FROM 'on'`) |
| `v_uid IS NULL` + `app.finance_pti_enabled='on'` | povolené (GUC sa ignoruje) | povolené **iba ak GUC explicitne nastavila `finance_pti_enable()`** ✅ explicitná hranica dôvery |

Nezmenené v OBOCH variantoch (invarianty 5 a 6): `DRAFT/POSTED/VOID` prechody, nemennosť
POSTED riadku, `VOID` finálny, `DELETE` iba `DRAFT`, stampovanie `created_by/updated_by/posted_by`.

### 5.3 Kto sa vôbec dostane k `auth.uid() IS NULL` (kto funkciu volá)

| Kontext | Ako vzniká NULL uid | Kto kontroluje | Zdroj |
|---|---|---|---|
| Aplikácia (SSR server actions) | **NEVZNIKNE** — `createClient()` pracuje s JWT prihláseného používateľa | guard + RLS | `src/app/dashboard/finance/actions.ts:90-96` (insert), `:123-138` (RPC) |
| `anon` role | nemá GRANT na `finance_transactions` | tabuľkové práva + RLS | `20261015:263-264` (`GRANT … TO authenticated` / `TO service_role`; **anon bez grantu**) |
| `authenticated` bez `sub` v tvrdeniach (hypotetické) | uid NULL | **RLS aj tak zamietne** — politiky `TO authenticated` volajú `has_permission((SELECT auth.uid()), …)` = `false` | `20261015:323-343` |
| `service_role`, vlastník DB, SQL editor | uid NULL, **RLS obídené** (GRANT ALL / bypassrls) | **iba guard** → pri K13.2.4 tu autorizácia **nefunguje** | `20261015:264` |
| Edge funkcia `send-push` | používa service_role | **nedotýka sa financií** — `.from("push_subscriptions")` len SELECT/DELETE | `supabase/functions/send-push/index.ts:133,169` |

**Kľúčové statické zistenie:** v `src/` sa **0×** vyskytuje `service_role` / `SUPABASE_SERVICE_ROLE`
(rekurzívne prehľadanie `*.ts/*.tsx`). Bežní používatelia aplikácie preto majú **vždy neprázdny
uid** a obe varianty sa pre nich správajú **rovnako prísne**. Reálny dosah K13.2.4 je
**strata druhej línie obrany** v kontextoch obchádzajúcich RLS (service_role/vlastník) a
**porušenie požadovanej invariany** — nie priamy eskalačný vektor cez PostgREST (to potvrdzuje
aj RLS `WITH CHECK has_permission(auth.uid(),…)`). Tento záver je statický; **runtime
potvrdenie RLS matice = BLOCKED**.

### 5.4 Slabé miesta K13.2.5 modelu (musia sa overiť pred nasadením)

1. **`session_user` vs `authenticator`:** `finance_pti_enable()` púšťa iba
   `session_user IN ('service_role','postgres')` (riadok 62). Ak PostgREST pripája ako
   `authenticator` (štandard Supabase), funkcia by **hodila výnimku aj pre legitímny
   service_role** → efekt je *fail-closed* (bezpečné), ale serverové operácie by boli
   **blokované**. **NEOVERENÉ — musí sa zmerať na DEV.**
2. **Vlastníctvo GUC:** `set_config('app.…')` pre vlastné (dvojdielne) GUC nemá samostatné
   oprávnenie — hranica dôvery stojí na tom, že klient cez PostgREST **nevie spustiť
   ľubovoľný SQL/SET**. V migráciách existuje **práve jeden** `set_config` volajúci
   (`finance_pti_enable`, `20261022_…:65`) a žiadny iný RPC GUC nenastavuje (staticky overené).
   Runtime test musí skúsiť, či `authenticated` vie GUC ovplyvniť dostupnými cestami.
3. **Životnosť GUC:** `set_config(..., true)` je transaction-local → po skončení požiadavky
   odpadá (statická znalosť API; odporúča sa runtime test na poolovanom spojení).

### 5.5 Vyhodnotenie požiadaviek invarianty

1. ✅ (navrhnutý stav) Finančná operácia neprejde bez autorizácie — pri uid aj pri NULL.
2. ✅ NULL uid **neautomaticky preskakuje** autorizáciu — vyžaduje explicitný GUC.
3. ✅ Používa sa existujúce `finance.edit` cez existujúce `public.has_permission`.
4. ✅ Žiadny nový permission key (žiadne `finance.post`/`finance.void`).

6. ✅ Nemennosť transakcií a transferov zachovaná (guard + `finance_guard_transfer_group`).
7. ✅ RLS a audit nedotknuté (žiadna z 20261022 migrácií politiky/RLS nemení).
8. ⚠ Overiť runtime: žiadna alternatívna RPC cesta nenapíše `finance_transactions` mimo
   guardu (pozri §6 — staticky je taká len `finance_create_transfer`, ktorá má vlastné

### 7.2 Požiadavky na opravnú migráciu (splnené návrhom v §8)

- **Deterministická:** jediný `CREATE OR REPLACE FUNCTION public.finance_guard_transactions()`
  s konečnou (hardened) semantikou → posledná aplikovaná definícia je vždy tá správna,
  nech je poradie dvoch `20261022` súborov akékoľvek.
- **Nezávisí od poradia konfliktných historických migrácií:** značka `20261025` > `20261024` >
  `20261022`.
- **Idempotentná:** `CREATE OR REPLACE FUNCTION` + `DROP TRIGGER IF EXISTS` / `CREATE TRIGGER`
  + `CREATE OR REPLACE FUNCTION` helperu (opakované spustenie je bezpečné).
- **Zachová granty, trigger väzby a bezpečnostné vlastnosti:** tie isté `REVOKE/GRANT` ako
  existujúce migrácie, `SECURITY DEFINER`, `SET search_path = public`, trigger
  `BEFORE INSERT OR UPDATE OR DELETE … FOR EACH ROW`.
- **Neodstráni legitímne ochrany:** RLS politiky, audit trigger, transfer guard, pravidlá
  `DRAFT/POSTED/VOID` a nemennosti zostávajú nedotknuté (opravná migrácia ich nespomína).
- **Kompatibilná so schémou:** žiadne nové tabuľky, stĺpce, roly ani permission keys;
  používa len `public.has_permission(uuid,text)` a `auth.uid()`.
- **Opraví aj syntaktickú chybu K13.2.5** (chýbajúci `END IF`) — telo v §8 je štruktúrne
  vyvážené (skontrolované počtom `IF`/`END IF` = 24/24 — pozri §8).
- **Signatúra sa NEMENÍ** → nič sa nerozbije (guard nikto nevolá priamo, pozri §6.4).

## 8. SQL NÁVRH NA KONTROLU — **NEAPLIKOVAŤ** (KROK 5 / výstup bod 8)

> **TOTO NIE JE SCHVÁLENÉ NA NASADENIE.** Súbor sa v tejto fáze **NEVYTVÁRA** a SQL sa
> **nespúšťa**. Návrh je vložený len na odbornú kontrolu. Po schválení by vznikol nový súbor
> `dhz-app/supabase/migrations/20261025_finance_guard_transactions_authoritative_fix.sql`
> (názov orientačný; rozhodujúce je, aby značka bola **> 20261024**).

```sql
-- ============================================================================
-- NÁVRH (len na kontrolu) — K13.4.5 forward-only fix
-- Predpoklad: časová značka 20261025 > 20261024 > 20261022
-- Účel: deterministicky nastaviť FINÁLNU bezpečnú definíciu finance_guard_transactions()
--       nezávisle od poradia dvoch konfliktných migrácií 20261022.
-- Idempotentné: CREATE OR REPLACE + DROP TRIGGER IF EXISTS / CREATE TRIGGER.
-- NEMENÍ: RLS, politiky, roly, granty tabuliek, audit, transfer guard, históriu.
-- ============================================================================

-- 1) Explicitná hranica dôvery pre kontexty bez identity (service_role / vlastník).
CREATE OR REPLACE FUNCTION public.finance_pti_enable()
RETURNS void
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
BEGIN
    IF session_user <> 'service_role' AND session_user <> 'postgres' THEN
        RAISE EXCEPTION 'finance_pti_enable() je volna iba pre service_role alebo DB vlastnika';
    END IF;
    PERFORM set_config('app.finance_pti_enabled', 'on', true);
    RETURN;
END;
$$;

REVOKE ALL ON FUNCTION public.finance_pti_enable() FROM public, anon;
GRANT EXECUTE ON FUNCTION public.finance_pti_enable() TO service_role;

-- 2) Autoritatívna definícia guardu (semantika K13.2.5 + OPRAVENÁ štruktúra IF/END IF).
CREATE OR REPLACE FUNCTION public.finance_guard_transactions()
RETURNS TRIGGER
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
    v_uid uuid := auth.uid();
BEGIN
    -- ---------------- INSERT ----------------
    IF TG_OP = 'INSERT' THEN
        IF v_uid IS NOT NULL THEN
            NEW.created_by := v_uid;
            NEW.updated_by := v_uid;
        END IF;

        -- Priama tvorba POSTED riadku vyžaduje finance.edit, ALEBO explicitnú
        -- dôveryhodnú hranicu (GUC nastavený výhradne finance_pti_enable()).
        -- Chýbajúca identita NIKDY sama o sebe autorizáciu nepreskočí.
        IF NEW.status = 'POSTED' THEN
            IF v_uid IS NOT NULL THEN
                IF NOT public.has_permission(v_uid, 'finance.edit') THEN
                    RAISE EXCEPTION
                        'Creating a POSTED transaction requires finance.edit permission';
                END IF;
            ELSIF current_setting('app.finance_pti_enabled', true) IS DISTINCT FROM 'on' THEN
                RAISE EXCEPTION
                    'Creating a POSTED transaction requires finance.edit or an explicit trusted context (SELECT public.finance_pti_enable() to set app.finance_pti_enabled = on)';
            END IF;
            NEW.posted_at := COALESCE(NEW.posted_at, NOW());
            IF v_uid IS NOT NULL THEN
                NEW.posted_by := v_uid;
            END IF;
        END IF;

        RETURN NEW;
    END IF;

    -- ---------------- UPDATE ----------------
    IF TG_OP = 'UPDATE' THEN
        IF v_uid IS NOT NULL THEN
            NEW.updated_by := v_uid;
        END IF;

        -- POSTED riadok možno len stornovať a len s finance.edit / GUC hranicou.
        IF OLD.status = 'POSTED' THEN
            IF NEW.status <> 'VOID' THEN
                RAISE EXCEPTION
                    'A POSTED transaction cannot be modified; only voiding is allowed';
            END IF;
            IF v_uid IS NOT NULL THEN
                IF NOT public.has_permission(v_uid, 'finance.edit') THEN
                    RAISE EXCEPTION 'Voiding a transaction requires finance.edit permission';
                END IF;
            ELSIF current_setting('app.finance_pti_enabled', true) IS DISTINCT FROM 'on' THEN
                RAISE EXCEPTION
                    'Voiding a posted transaction requires finance.edit or an explicit trusted context (SELECT public.finance_pti_enable() to set app.finance_pti_enabled = on)';
            END IF;
            -- Nemennosť finančnej identity POSTED riadku (zachovaná).
            IF NEW.amount_minor <> OLD.amount_minor
               OR NEW.account_id <> OLD.account_id
               OR NEW.type <> OLD.type
               OR NEW.transaction_date <> OLD.transaction_date
               OR NEW.transfer_group_id IS DISTINCT FROM OLD.transfer_group_id THEN
                RAISE EXCEPTION
                    'Amount/account/type/date of a POSTED transaction are immutable';
            END IF;
            RETURN NEW;
        END IF;

        -- VOID riadok je finálny (zachované).
        IF OLD.status = 'VOID' THEN
            RAISE EXCEPTION 'A VOID transaction is immutable';
        END IF;
        -- DRAFT -> POSTED: finance.edit alebo explicitná hranica dôvery.
        IF OLD.status = 'DRAFT' AND NEW.status = 'POSTED' THEN
            IF v_uid IS NOT NULL THEN
                IF NOT public.has_permission(v_uid, 'finance.edit') THEN
                    RAISE EXCEPTION 'Posting a transaction requires finance.edit permission';
                END IF;
            ELSIF current_setting('app.finance_pti_enabled', true) IS DISTINCT FROM 'on' THEN
                RAISE EXCEPTION
                    'Posting a transaction requires finance.edit or an explicit trusted context (SELECT public.finance_pti_enable() to set app.finance_pti_enabled = on)';
            END IF;
            NEW.posted_at := COALESCE(NEW.posted_at, NOW());
            IF v_uid IS NOT NULL THEN
                NEW.posted_by := v_uid;
            END IF;
        END IF;   -- << CHÝBAJÚCI END IF V SUBORE 20261022_finance_transaction_guard_fix.sql

        -- DRAFT -> VOID: finance.edit alebo explicitná hranica dôvery.
        IF OLD.status = 'DRAFT' AND NEW.status = 'VOID' THEN
            IF v_uid IS NOT NULL THEN
                IF NOT public.has_permission(v_uid, 'finance.edit') THEN
                    RAISE EXCEPTION 'Voiding a transaction requires finance.edit permission';
                END IF;
            ELSIF current_setting('app.finance_pti_enabled', true) IS DISTINCT FROM 'on' THEN
                RAISE EXCEPTION
                    'Voiding a transaction requires finance.edit or an explicit trusted context (SELECT public.finance_pti_enable() to set app.finance_pti_enabled = on)';
            END IF;
        END IF;

        RETURN NEW;
    END IF;

    -- ---------------- DELETE ----------------
    IF TG_OP = 'DELETE' THEN
        IF OLD.status <> 'DRAFT' THEN
            RAISE EXCEPTION
                'Only DRAFT transactions may be deleted; use void for posted history';
        END IF;
        RETURN OLD;
    END IF;

    RETURN NULL;
END;
$$;

REVOKE ALL ON FUNCTION public.finance_guard_transactions() FROM public, anon;
GRANT EXECUTE ON FUNCTION public.finance_guard_transactions() TO authenticated, service_role;

-- 3) Napojenie triggera (idempotentné).
DROP TRIGGER IF EXISTS finance_transactions_guard ON public.finance_transactions;
CREATE TRIGGER finance_transactions_guard
BEFORE INSERT OR UPDATE OR DELETE ON public.finance_transactions
FOR EACH ROW
EXECUTE FUNCTION public.finance_guard_transactions();
```
