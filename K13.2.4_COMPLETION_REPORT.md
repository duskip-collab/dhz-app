## 4. Zistenia a opravy

### M1 — KRITICKÁ · Guard z `20261020` robil autorizáciu → blokoval existujúci test

**Dôkaz (2 nezávislé prejavy):**

1. **`has_permission(NULL, ...)` je vždy `false`.** Všetky EXISTS poddotazy
   porovnávajú `ur.user_id = NULL`, čo nie je nikdy pravdivé
   (`20261006:321-352`). Guard volal
   `IF NOT public.has_permission(v_uid, 'finance.create') THEN RAISE`
   **bez** podmienky na `v_uid IS NULL` → v každom kontexte s NULL
   `auth.uid()` (service_role, vlastník DB, SQL editor) bol zápis **vždy**
   zamietnutý.

2. **Horší prípad — `auth.uid()` nie je NULL, ale guard predsa blokuje.**
   `RESET ROLE` resetuje **iba rolu**, nie custom GUC `request.jwt.claims`.
   Existujúci test `supabase/tests/k13_finance_runtime_test.sql`:
   * riadok 654: `SET LOCAL "request.jwt.claims" = '{"sub":"1111..."}'`
     (= `none_user`, žiadne finance oprávnenia),
   * riadok 677 + 687: `RESET ROLE` → beží ako **vlastník DB**, RLS sa
     **neaplikuje**,
   * riadok 716: `INSERT INTO public.finance_transaction_attachments ...`

   Guard vidí `auth.uid() = 1111...` → `has_permission` = false → **RAISE**.
   → **Existujúci test 7a by po aplikácii 20261020 zlyhal.**

**Overené dodatočne:** žiadny test nikdy nevyčistí `request.jwt.claims`
(0 výskytov `= ''` / `= '{}'`), takže únik identity je systematický.

**OPRAVA:** nová migrácia
`supabase/migrations/20261021_finance_attachments_guard_fix.sql` —
`CREATE OR REPLACE FUNCTION`, funguje **či už bola 20261020 aplikovaná alebo
nie**.

Guard si necháva **výhradne invarianty integrity** (to, čo RLS vyjadriť nevie):

1. `uploaded_by := auth.uid()` pri existujúcom `auth.uid()` (anti-spoofing),
2. väzba cesty: prvý segment `storage_path` == `transaction_id`,
3. rodicovská transakcia existuje a je `DRAFT`,
4. `transaction_id` je nemenný pri UPDATE.

**Autorizácia bola z guardu ÚPLNE ODSTRÁNENÁ** — rieši ju RLS
(`finance_attach_select/insert/update/delete`, `20261015:367-386`), ktoré pre
rolu `authenticated` kontroluje `finance.view` / `finance.create` /
`finance.edit`.

**Prečo je to bezpečné:** duplicita autorizácie v triggery bola nielen
zbytočná, ale **aktívne škodlivá** — mohla byť prísnejšia ako RLS a zamietať
operácie, ktoré RLS povoľuje (presne prípad M1). Guard už RLS neduplikuje ani
neprekračuje. Anti-spoofing identity — pôvodný cieľ 20261020 — zostáva plne
aktívny.
