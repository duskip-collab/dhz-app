## 3. Navrhovaný dátový model

### 3.1 Nová tabuľka `public.invitations`

```sql
CREATE TABLE public.invitations (
  id             uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  code_hash      text        NOT NULL UNIQUE,   -- sha256 hex(normalizovaný kód)
  role_id        uuid        NOT NULL REFERENCES public.roles(id) ON DELETE RESTRICT,
  created_by     uuid        NOT NULL REFERENCES auth.users(id) ON DELETE RESTRICT,
  created_at     timestamptz NOT NULL DEFAULT now(),
  expires_at     timestamptz NOT NULL,
  is_active      boolean     NOT NULL DEFAULT true,
  consumed_by    uuid        REFERENCES auth.users(id) ON DELETE SET NULL,
  consumed_at    timestamptz,
  consumed_email text,
  status         text        NOT NULL DEFAULT 'pending'
                 CHECK (status IN ('pending','consumed','revoked','expired')),
  consumed_state text        NOT NULL DEFAULT 'none'
                 CHECK (consumed_state IN ('none','pending_role','complete')),
  notes          text,
  updated_at     timestamptz NOT NULL DEFAULT now()
);

CHECK (consumed_at IS NULL OR consumed_by IS NOT NULL);
CHECK (expires_at > created_at);
```

- `role_id` → FK na `roles` zabezpečuje, že rola je **existujúca kanonická** (seed z `20261006`). Server navyše validuje `isAppRole(role)` pred vložením.
- `status` = odvodený stav (trigger udržiava konzistenciu), `consumed_state` rieši čiastočné zlyhanie (§4.3).
- `code_hash` je **iba hash** – raw kód sa v DB neukladá vôbec.
- `notes` = voliteľná poznámka administrátora (bez citlivých údajov).

### 3.2 Normalizácia a generovanie kódu

- Formát: `XXXX-XXXX-XXXX` (3 skupiny po 4 znaky z bezpečnej abecedy bez `0/O/1/I`), **12 znakov ≈ 60 bitov**.
- Zdroj entropie: `crypto.getRandomValues` (Web Crypto, dostupný v Node 18+ aj edge runtime) – **nie** `Math.random`.
- Normalizácia pred hashom: `trim().toUpperCase().replace(/[^A-Z0-9-]/g,"")` – identická v TS aj SQL (aby sedel hash).
- Hash: `sha256(normalizovaný_kód)` → hex; SQL: `encode(digest(...::bytea,'sha256'),'hex')` (pgcrypto, už používané v `20261108`).
- **Prečo SHA-256 a nie bcrypt/argon2:** kód má vysokú entropiu (60 bitov) ⇒ offline brute-force je nerelevantný; SHA-256 dovolí deterministické lookup a index. Konzistentné s `member_access_codes`.

### 3.3 Priradenie roly novému účtu (dôležité zistenie)

`public.user_roles` má PK `(user_id, role_id)` a **žiadny `id`**. `admin.service.ts::setUserRole()` robí:
```ts
supabase.from("user_roles").update({ role_id }).eq("user_id", userId);
```
Pre **nového** používateľa bez riadku tento UPDATE nespraví nič (0 riadkov, bez chyby) → nový účet by ostal bez role. Preto:
- priradenie robíme **INSERT** do `user_roles` (`ON CONFLICT DO NOTHING`), ideálne cez RPC `consume_invitation(...)`;
- **neopravujeme** `setUserRole()` v tejto fáze (scope K17.5) – zapíšeme to do §8 ako follow-up.

### 3.4 Oprávnenie na správu pozvánok

- `admin.users` (`PERMISSIONS.ADMIN_USERS`) je **postačujúce**: admin UI už na ňom stojí (`admin/page.tsx`) a semantically zodpovedá „správa používateľov a prístupov“.
- **Nové oprávnenie nevytvárame** (brief: nevytváraj, kým analýza nepreukáže potrebu). Rozsah „vytvoriť účet s rolou“ spadá do `admin.users`.
- RLS použije `public.has_permission(auth.uid(),'admin.users')` – konzistentné s TS `requirePermission(PERMISSIONS.ADMIN_USERS)`.
- `VELITEL` **nedostane** správu pozvánok (dnes má prístup ku `member_access_codes`; iná oblasť, nemení sa).

### 3.5 Audit

Použije sa existujúca `public.audit_log` (`action`, `module`, `entity_type`, `entity_id`, `old_data`, `new_data`).

| Udalosť | `action` | `module` | `entity_type`/`entity_id` | `new_data` |
|---|---|---|---|---|
| Vytvorenie | `invitation.created` | `admin` | `invitation` / id | `{ role_code, expires_at }` – **bez kódu a hashu** |
| Deaktivácia | `invitation.revoked` | `admin` | `invitation` / id | `{ reason }` |

Zmena jej sémantiky by porušila existujúci prihlasovací tok (`resolve_access_code` + `signInWithPassword`) a vytvorila by rozpor s kanonickým modelom. → **Nová tabuľka `invitations`.**

## 4. Bezpečný registračný tok (návrh, neimplementovaný)

### 4.1 Aktivity a komponenty

1. **Admin vytvorí pozvánku**
   - Server Action `createInvitationAction` → `requirePermission(ADMIN_USERS)` (fail-closed).
   - Validácia: `role_code` musí byť v `APP_ROLES` (`isAppRole`) **a** existovať v `roles` (FK).
   - Generovanie kódu (60 bitov) → `code_hash` → insert cez RPC `create_invitation` (aby sa audit zapísal v DB).
   - **Raw kód sa vráti raz** v odpovedi server action → dialóg s tlačidlom „Skopírovať“. Raw kód sa nikam neukladá (ani DB, ani log).

2. **Nový používateľ otvára `/register`**
   - Obrazovka: e-mail, heslo, potvrdenie hesla, pozvánkový kód.
   - Klient zavolá `supabase.auth.signUp({ email, password })` (bežný Supabase flow; e-mail potvrdenie podľa nastavenia projektu).
   - **Rola sa nikdy nečíta z formulára.**

3. **Server overí a spotrebuje pozvánku**
   - Server Action `acceptInvitationAction({ email, code })`:
     a. **Resolve** kódu: RPC `resolve_invitation_role(p_code text)` → `SECURITY DEFINER`, `search_path = public, extensions`, `GRANT EXECUTE TO anon, authenticated`; vracia `{ invitation_id, role_code }` iba pre `status='pending' AND is_active AND expires_at > now()`.
     b. Overiť, že používateľ s daným e-mailom existuje v `auth.users` a má `email_confirmed_at IS NOT NULL` (aby sa nedal spáliť kód na nepotvrdený účet).
     c. **Atomicky spotrebovať:** RPC `consume_invitation(p_invitation_id uuid, p_user_id uuid, p_email text)` – pozri §6.4.
     d. **Prideliť rolu:** v tej istej RPC `INSERT INTO public.user_roles(user_id, role_id) … ON CONFLICT DO NOTHING` – rola pochádza **iba** z pozvánky.
     e. `UPDATE invitations SET consumed_state='complete', status='consumed'`.
     f. Audit `invitation.consumed` + `invitation.role_assigned`.

   - Poradie: **najprv spotreba (rezervácia), potom priradenie roly.** Ak priradenie zlyhá, pozvánka ostáva `pending_role` (nie je vratná → žiadny druhý účet) a recovery ju rieši admin (§4.3).

4. **Prvé prihlásenie**
   - Po potvrdení e-mailu (alebo pri `email_confirmations = false`) sa používateľ prihlási **e-mailom + vlastným heslom** (`EmailLoginForm`).
   - `is_email_login_allowed` (RPC) dnes povoľuje e-mailové prihlásenie len ADMIN-om a členom s e-mailom v profile. → **Nový používateľ registrovaný pozvánkou nemusí byť členom** ⇒ treba rozšíriť `is_email_login_allowed` o „potvrdený účet, ktorý má rolu z pozývacej“. Je to **jediný** nutný zásah do existujúceho login RPC (doplnenie, nie zmena sémantiky) – vyžaduje samostatné schválenie (§8.2 O1).

### 4.2 Explicitné scenáre chýb

| Scenár | Správanie | Mechanizmus |
|---|---|---|
| Neplatný kód | „Pozývací kód nie je platný.“ | `resolve_invitation_role` nevráti nič; bez detailov |
| Expirovaný kód | „Pozývací kód expiroval.“ | `expires_at > now()` |
| Deaktivovaný kód | „Pozývací kód bol zrušený.“ | `is_active = false` |
| Už spotrebovaný kód | „Pozývací kód bol už použitý.“ | `consumed_at IS NOT NULL` → 0 riadkov z `UPDATE` |
| **Súbežné uplatnenie** | Iba jeden výsledok `UPDATE … RETURNING` | MVCC/row lock; druhá transakcia vidí `consumed_at` → 0 riadkov |
| Opakovanie po chybe siete | Idempotentné, bez druhého účtu | `consume_invitation` viazaná na `(invitation_id, user_id)`; `signUp` s existujúcim e-mailom → bez session ⇒ server odmietne („účet už existuje“) |
| Zlyhanie vytvorenia účtu po overení kódu | Kód **ne** je spotrebovaný (spotreba až po potvrdení existencie účtu) | používateľ môže retry; kód ostáva `pending` |
| Zlyhanie priradenia roly po spotrebe | Účet existuje, rola chýba; `consumed_state='pending_role'` | recovery §4.3; kód sa **ne** vracia do `pending` |
| Duplicitný účet / existujúca identita | Odmietnuté, bez druhého profilu | `signUp` s existujúcim e-mailom + kontrola `auth.users`; `profiles.id` = `auth.users.id` |
| Pokus o zvýšenie role cez formulár | Ignorované / odmietnuté | rola sa číta len z pozvánky; žiadny klientský vstup do `user_roles` |

### 4.3 Recovery po čiastočnom zlyhaní (bez druhého účtu / bez nesprávnej role)

- `consumed_state = 'pending_role'` = „účet existuje, rola ešte nie“. Kód ostáva `status='consumed'` (nepoužiteľný).
- Recovery: **admin** (s `admin.users`) vidí pozvánku v stave „čaká na rolu“ a môže:
  - priradiť rolu ručne cez existujúci `setUserRole` (s fixom na INSERT – §3.3), alebo
  - RPC `recover_invitation_role(p_invitation_id)` (definer, len `admin.users`), ktorá zopakuje INSERT roly z `invitations.role_id` a nastaví `consumed_state='complete'`.
- **Žiadny spôsob, ktorým by sa kód mohol použiť na druhý účet**: `consumed_at` sa nikdy nenuluje.

### 4.5 Používateľský tok zdieľania pozývacieho kódu (WhatsApp / Messenger / kopírovanie / systém)

**Cieľ:** administrátor po vytvorení pozvánky dostane kód a pripravený pozývací text a môže ho poslať novému členovi cez ľubovoľný kanál bez toho, aby aplikácia bola závislá od konkrétnej platby.

**Bezpečnostná zásada (preemptívna, platí pre celú sekciu):**
- Aplikácia **nikdy neposiela** pozvánku sama (žiadne Graph API, žiadne WhatsApp Business API, žiadne SMTP na kód).
- Otvorenie WhatsApp/Messenger okna alebo zdieľacieho háku **nie je potvrdením odoslania**. UI musí to používateľovi výslovne oznámiť.
- Bezpečnosť pozvánky (jednorazovosť, expirácia, rola) sa **nesmie** opierať o kanál zdieľania. Kanál je iba preprava textu; platnosť overuje až server (§6.4).

#### 4.5.1 Kanály a ich podpora

| Kanál | Mechanizmus | Podpora | Poznámka |
|---|---|---|---|
| Kopírovanie **kódu** | `navigator.clipboard.writeText(code)` | ✅ vždy | fallback: textarea + `document.execCommand('copy')` pre nepodporované prehliadače/HTTP |
| Kopírovanie **celého textu** | `navigator.clipboard.writeText(message)` | ✅ vždy | fallback ako vyššie |
| **WhatsApp** | `https://wa.me/?text=<encodeURIComponent(message)>` | ✅ oficiálny web deep-link | Otvorí WhatsApp (web/app) s predvyplnenou správou; **užívateľ musí potvrdiť odoslanie** |
| **Messenger** | Primárne: kopírovanie textu + vloženie do Messenger (nemá oficiálny univerzálny deep-link na ľubovoľný text bez konkrétneho profilu/obchodu). Voliteľne: Facebook Send Dialog `https://www.facebook.com/dialog/send?app_id=<ID>&link=<URL>&redirect_uri=<URI>&text=<...>` | ⚠️ podmienené | Vyžaduje Meta App ID a schválenú doménu; bez nich tlačidlo **nie je zobrazené** (graceful degradation) — nikdy sa neskrýva chyba |
| **Systémové zdieľanie** | `navigator.share({ title, text, url })` (Web Share API) | ✅ ak podporuje prehliadač/PWA | `navigator.canShare?.({ files })` – textový share je vždy OK; použitie len na užívateľský gesture (click) |

**Reuse existujúceho vzoru:** `dhz-app/src/features/admin/components/AdminMemberManager.tsx` (riadky 226–252) už používa presne tento pattern (`navigator.share` → fallback `wa.me`) pre *prístupový kód*. Nový tok ho **neskopíruje naslepo** – rozšíri ho o „Skopírovať kód“ / „Skopírovať text“ a o Messenger vetvu s podmienkou na dostupnosť.

#### 4.5.2 Predvyplnená pozývací správa

Predvyplnený text (zostaví **klient** z údajov, ktoré server vrátili; žiadny kód sa neposiela cez URL ani cez analytics):

```
DHZ RUŽINDOL – pozvanie do DHZ Digital OS

Dobrý deň,
dostali ste pozvanie do digitálneho organizačného systému DHZ RUŽINDOL
(DHZ Digital OS) s rolou: {ROLE_LABEL}.

Váš jednorazový pozývací kód:
{CODE}

Platnosť kódu: {EXPIRES_AT}
Registrácia: {REGISTRATION_URL}

Postup:
1. Otvorte {REGISTRATION_URL}
2. Zadajte e-mail, siľnú heslo a tento pozývací kód
3. Potvrďte registráciu a prihláste sa

Kód je jednorazový a po registrácii stráca platnosť.
```

- `{REGISTRATION_URL}` sa **doplní až po overení reálnej URL**. Overené z repozitára: route `/register` **dnes neexistuje** (`src/app/` obsahuje len `(app)`, `api`, `dashboard`, `login`). Plán ho zavádza (§5, nový súbor `src/app/register/page.tsx`). Preto:
  - do implementácie sa **nezadáva natvrdo** URL z domnienky,
  - URL sa preberá z runtime konfigurácie (`NEXT_PUBLIC_APP_URL` / `window.location.origin`) a validuje sa, že cesta `/register` skutočne existuje (404 = tlačidlo „Zdieľať s odkazom“ sa vypne alebo sa zobrazí bez URL s varovaním),
  - kým route neexistuje, zdieľací text sa zostaví **bez** odkazu a používateľ sa zobrazí upozornenie, že odkaz sa doplní po vytvorení registračnej stránky.
- `{ROLE_LABEL}` z `ROLE_LABELS` (`src/lib/auth/roles.ts`) – neposiela sa kód role, ktorý by používateľ mohol zmeniť; rolu aj tak priraďuje server z pozvánky (§4.1 krok 3).

#### 4.5.3 UI prvky (v dialógu po vytvorení pozvánky)

Dialóg „Pozvánka vytvorená“ (raw kód zobrazený **raz**, §4.4 bod 2) obsahuje:

1. **Kód** – veľký monospace text, tlačidlo **„Skopírovať kód“** (feedback „Skopírované“ po ~2 s).
2. **Pozývací text** – textarea s náhľadom, tlačidlo **„Skopírovať text“**.
3. **Tlačidlá zdieľania:**
   - „WhatsApp“ → otvorí `wa.me` s predvyplneným textom,
   - „Messenger“ → zobrazí sa **iba ak** je nakonfigurovaný Facebook App ID (§4.5.1); inak sa skryje,
   - „Zdieľať“ → `navigator.share` (ak je dostupné); inak sa tlačidlo skryje.
4. **Explicitné upozornenie:** *„Otvorenie aplikácie neznamená, že správa bola odoslaná. Po otvorení ju, prosím, poslite a uveďte, že ste ju poslali.“*
5. **Bezpečnostná poznámka:** *„Kód platí do {EXPIRES_AT} a je jednorazový. Ak sa dostal k niekomu cudziemu, pozvánku zrušte.“*
6. Po zatvorení dialógu sa raw kód **vymaže zo stavu** (React state) a už sa nedá získať (v DB je len `code_hash`).

#### 4.5.4 Kľúčové bezpečnostné vlastnosti zdieľania

| # | Vlastnosť | Ako sa zabezpečuje |
|---|---|---|
| S1 | Kód sa nezapisuje do URL | `wa.me` link nesie iba text; žiadny query parameter s kódom |
| S2 | Kód sa nezapisuje do logov ani analytics | `console.*` bez payloadu; žiadny analytics event s kódom |
| S3 | Kód sa nezapisuje do `audit_log` | §3.5 / §6.6 |
| S4 | Kód nie je v prehliadačovej URL ani v localStorage | kód existuje len v reakčnom stave dialógu; po zatvorení zahodený |
| S5 | Otvorenie kanála ≠ odoslanie | používateľský text v dialógu + žiadny stav „odoslané“ |
| S6 | Kanál neovplyvňuje platnosť | platnosť overuje server (`expires_at`, `consumed_at`) |
| S7 | Rola sa nedá zmeniť cez kód/text | rola je FK z `invitations.role_id`, serverovo whitelistovaná (§3.4, §6.4) |
| S8 | Žiadne automatické odosielanie | v K17.5 žiadne externé API; iba otvorenie deep-linku |

```sql

CREATE POLICY invitations_select_admin ON public.invitations
  FOR SELECT TO authenticated
  USING (public.has_permission((SELECT auth.uid()), 'admin.users'));

  FOR INSERT TO authenticated
  WITH CHECK (public.has_permission((SELECT auth.uid()), 'admin.users')

  FOR UPDATE TO authenticated
  USING (public.has_permission((SELECT auth.uid()), 'admin.users'))
  WITH CHECK (public.has_permission((SELECT auth.uid()), 'admin.users'));
```

**Ochrana pred svojvoľným zvýšením role:** `role_id` je FK na `roles` ⇒ nemožno uložiť neexistujúcu rolu; server navyše validuje `isAppRole()` a RPC `create_invitation` prijíma **iba `p_role_code` z whitelistu** (mirror `APP_ROLES`) a `role_id` vyberá interne. Klient nikdy neposiela `role_id`.


### 6.3 RPC (bezpečnostné vlastnosti)

Všetky RPC: `SECURITY DEFINER`, `SET search_path = public, extensions`, `REVOKE ALL … FROM PUBLIC` + explicitný `GRANT EXECUTE`.

| Funkcia | Signatúra | Kto môže volať | Čo robí |
|---|---|---|---|
| `create_invitation` | `(p_role_code text, p_expires_at timestamptz, p_code_hash text) → uuid` | `authenticated` s `admin.users` | whitelist role, validuje `expires_at`, INSERT, audit `invitation.created` |
| `resolve_invitation_role` | `(p_code text) → table(invitation_id uuid, role_code text)` | `anon`, `authenticated` | vráti rolu len pre platnú/neexpirovanú/nespotrebovanú pozvánku |
| `consume_invitation` | `(p_invitation_id uuid, p_user_id uuid, p_email text) → uuid` | `anon`, `authenticated` | atomický UPDATE + INSERT `user_roles` + audit |
| `revoke_invitation` | `(p_invitation_id uuid) → void` | `authenticated` s `admin.users` | `is_active=false`, `status='revoked'`, audit |
| `recover_invitation_role` | `(p_invitation_id uuid) → void` | `authenticated` s `admin.users` | zopakuje INSERT roly, `consumed_state='complete'` |

### 6.4 `consume_invitation` – jadro bezpečnosti (jedna transakcia)

```sql
CREATE OR REPLACE FUNCTION public.consume_invitation(
  p_invitation_id uuid, p_user_id uuid, p_email text)
RETURNS uuid
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public, extensions
AS $$
DECLARE v_role_id uuid; v_role_code text;
BEGIN
  -- 1) atomická rezervácia (0 riadkov = kód je neplatný/expirovaný/spotrebovaný)
  UPDATE public.invitations i
     SET consumed_by = p_user_id, consumed_at = now(),
         consumed_email = lower(coalesce(p_email,'')), consumed_state = 'pending_role'
   WHERE i.id = p_invitation_id
     AND i.consumed_at IS NULL
     AND i.is_active
     AND i.status = 'pending'
     AND i.expires_at > now()
  RETURNING i.role_id INTO v_role_id;

  IF v_role_id IS NULL THEN
    RAISE EXCEPTION 'Invitation is not usable' USING ERRCODE = 'P0001';
  END IF;

  -- 2) rola pochádza IBA z pozvánky
  SELECT code INTO v_role_code FROM public.roles WHERE id = v_role_id;

  -- 3) idempotentné priradenie roly (INSERT, nie UPDATE)
  INSERT INTO public.user_roles (user_id, role_id)
  VALUES (p_user_id, v_role_id)
  ON CONFLICT (user_id, role_id) DO NOTHING;

  -- 4) stav
  UPDATE public.invitations
     SET status = 'consumed', consumed_state = 'complete'
   WHERE id = p_invitation_id;

  -- 5) audit BEZ raw kódu a hashu
  INSERT INTO public.audit_log (user_id, action, module, entity_type, entity_id, new_data)
  VALUES (p_user_id, 'invitation.consumed', 'auth', 'invitation', p_invitation_id,
          jsonb_build_object('role_code', v_role_code));

  RETURN v_role_id;
END;
$$;

REVOKE ALL ON FUNCTION public.consume_invitation(uuid, uuid, text) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION public.consume_invitation(uuid, uuid, text) TO anon, authenticated;
```

**Kľúčové vlastnosti:**
- `UPDATE ... WHERE consumed_at IS NULL` = jednorazovosť vynútená DB (nie aplikačnou kontrolou) ⇒ pri súbežných požiadavkách iba jeden vyhrá, druhý dostane 0 riadkov → výnimku.
- Celá funkcia je **jedna DB transakcia** ⇒ medzi spotrebovaním a priradením roly nie je medzera.
- `role_id` sa nikdy neprebíra z klienta.
- `audit_log` zápis neobsahuje kód ani hash.

### 6.5 Trigger na `invitations` (konzistencia stavu)

```sql
CREATE OR REPLACE FUNCTION public.invitations_set_state()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.consumed_at IS NOT NULL AND NEW.status = 'pending' THEN
    NEW.status := 'consumed';
  END IF;
  IF NEW.is_active = false AND NEW.consumed_at IS NULL THEN
    NEW.status := 'revoked';
  END IF;
  NEW.updated_at := now();
  RETURN NEW;
END;
$$;

CREATE TRIGGER invitations_set_state_trg
  BEFORE UPDATE ON public.invitations
  FOR EACH ROW EXECUTE FUNCTION public.invitations_set_state();
```
(Alternatívne: `expired` sa necháva vypočítať pri čítaní `expires_at > now()`.)

### 7.2 Akceptačné kritériá (Definition of Done)

1. Pozvánku vytvorí iba účet s `admin.users`; ostatné dostanú 403.
2. Kód sa v DB neukladá v surovej forme (iba `code_hash`); raw kód zobrazený raz.
3. Jednorazovosť je **vynútená databázou** (T14: 1 úspech z 2 paralelných requestov).
4. Rola priradená novému účtu pochádza **výhradne** z pozvánky; klientský vstup je ignorovaný (T19).
5. `user_roles` má po registrácii presne 1 nový riadok s očakávanou rolou.
6. Stav pozvánky je konzistentný (`pending`/`consumed`/`revoked`/`expired` + `consumed_state`).
7. `audit_log` obsahuje `invitation.created`, `invitation.consumed`, `invitation.revoked` **bez** raw kódu a hashu.
8. Chybové hlásky neodhalujú, či kód existoval.
9. `npx tsc --noEmit`, `npm run lint`, `npm run build` prejdú bez nových chýb.
10. `APP_ROLES` a `PERMISSIONS` sú **nezmenené**.
11. `member_access_codes` a jeho RPC sú **nezmenené**.
12. Migrácia je **forward-only** (žiadny `DROP` historických tabuliek, žiadny edit starších migrácií).
13. Dialóg pozvánky ponúka **skopírovanie kódu, skopírovanie textu, WhatsApp, Messenger (iba ak je podporovaný) a systémové zdieľanie**; pri nedostupnom kanáli sa tlačidlo skryje bez chyby.
14. UI **neuvádza, že správa bola odoslaná** – existuje len explicitné upozornenie, že otvorenie aplikácie nie je potvrdením odoslania.
15. Surový kód sa **neobjaví** v `audit_log`, v `console.*`, v URL ani v `localStorage`; po zatvorení dialógu sa odstráni zo stavu.
16. Odkaz na registráciu sa v pozývacej správe zobrazí **len ak** route existuje; inak text bez odkazu + varovanie.

## 8. Riziká a otvorené technické otázky

### 8.1 Riziká

| # | Riziko | Dopad | Mitigácia |
|---|---|---|---|
| R1 | `signUp` a zápis do `user_roles` **nie sú jedna transakcia** | účet existuje bez role | `consumed_state='pending_role'` + recovery (§4.3); `consumed_at` sa nikdy nenuluje |
| R2 | Kód je jediným preukazom do 14 dní | únik kódu = prístup | krátka expirácia (7–14 dní), hash v DB, možnosť zrušiť, audit |
| R3 | Používateľ zadá existujúci e-mail | prekrytie identity | `signUp` bez session + kontrola `auth.users` pred spotrebou |
| R4 | E-mail potvrdený až po spotrebe kódu | používateľ nemá prístup | `email_confirmed_at IS NOT NULL` ako podmienka spotreby |
| R5 | `audit_log` má `INSERT ... WITH CHECK (true)` | kdokoľvek authenticated môže falzifikovať audit | mimo scope; odporúčame follow-up sprísnenie RLS |
| R6 | `setUserRole()` robí UPDATE ⇒ nový účet bez role | účet bez oprávnení | K17.5 používa INSERT; follow-up oprava (§8.2 O2) |
| R7 | `is_email_login_allowed` pustí e-mail login len ADMIN/členom | nový používateľ sa nevie prihlásiť | rozšírenie RPC (§8.2 O1) – vyžaduje schválenie |
| R8 | `has_permission` je `SECURITY DEFINER` helper | vykonáva sa ako owner | konzistentné s `20261006`/`20261108` (repozitárny vzor) |
| R9 | DB chyba môže odhaliť detaily | information disclosure | server mapuje DB chyby na jednotné neutrálne texty |
| R10 | `crypto.getRandomValues` v edge runtime | dostupnosť API | overiť na `next build`; fallback `node:crypto` `randomBytes` |
| R11 | `console.error` s payloadom | únik kódu do logov | kód sa nikdy neloguje; v `catch` len kód chyby |
| R12 | Kód je v správe zdieľanej cez tretiu stranu | únik kódu mimo platformu | krátka expirácia (7–14 dní), zrušenie pozvánky, jednorazovosť; kanál nie je súčasťou bezpečnostného modelu |
| R13 | Užívateľ si myslí, že správa bola odoslaná | bez zásahu zostane člen bez prístupu | explicitné upozornenie v dialógu; žiadny stav „odoslané“ |
| R14 | `wa.me`/Messenger deep-link v inom prehliadači neexistuje | zdieľanie nefunguje | fallback: kopírovanie kódu/textu je vždy dostupné; tlačidlá sa degradujú bez chyby |
| R15 | Kód v URL deep-linku (napr. `link` parametr) | kód v browser history | kód je výhradne v tele správy; `link`/`redirect_uri` kód neobsahujú (T31/T33) |

### 8.2 Otvorené technické otázky (potrebujú rozhodnutie)

- **O1:** Smieme rozšíriť `is_email_login_allowed` (§4.1 krok 4)? Bez toho nový používateľ nevie prihlásiť e-mailom. Alternatíva: samostatný login tok pre pozvaných.
- **O2:** Opraviť `setUserRole()` na INSERT/upsert? Odporúčané, ale mimo scope K17.5.
- **O3:** Defaultná expirácia 7 alebo 14 dní? Plán používa 14.
- **O4:** Smie sa zrušiť aj spotrebovaná pozvánka (odobranie role)? Odporúčame nie (audit) – potvrdiť.
- **O5:** Kto smie vytvoriť pozvánku s rolou `ADMIN`? Odporúčame: iba účet, ktorý **sám** má `ADMIN` (aby `admin.users` bez ADMIN nemohol zvýšiť oprávnenia). Rozhodnúť.
- **O6:** Pridanie service_role kľúča? Plán sa mu vyhýba (klient `signUp`) ⇒ **nie je potrebné**.
- **O7:** Viazať pozvanie na konkrétny e-mail? Plán: nie (e-mail sa zistí pri registrácii). Alternatíva „invite-only email“ zvyšuje bezpečnosť, ale vyžaduje ďalšie pole.
- **O8:** Messenger – schváliť Meta App (Facebook App ID + `redirect_uri` na doménu projektu) pre plnú podporu tlačidla? Bez schválenia funguje Messenger len cez **kopírovanie textu** a vloženie do Messenger manuálne (tlačidlo Messenger sa nezobrazí).
- **O9:** Podporovať aj „zdieľanie cez e-mail“ (mailto:) a SMS (sms:) ako doplnok? Plán ich netyrpuje (nie sú v briefe), ale je to lacné doplnenie bez externého API.
- **O10:** Aká je reálna registračná URL? Potrebné overiť deployment doménu a či `NEXT_PUBLIC_APP_URL` existuje v `.env.local` (dnes: iba `NEXT_PUBLIC_SUPABASE_URL` a `NEXT_PUBLIC_SUPABASE_ANON_KEY` ⇒ treba pridať premennú alebo použiť `window.location.origin`).

## 9. Potvrdené zo zdrojového kódu vs. čo vyžaduje runtime overenie

### 9.1 Potvrdené zo zdrojového kódu (čitateľné v repozitári)
- Kanonické role `APP_ROLES` = ADMIN, VEDENIE, VELITEL, POKLADNIK, TRENER, CLEN, RODIC (`src/lib/auth/roles.ts`).
- Existujú `requirePermission` / `requireRole` / `getAuthContext` s fail-closed správaním (`src/lib/auth/server.ts`).
- Existuje oprávnenie `admin.users`; admin stránka je ním chránená (`src/app/(app)/admin/page.tsx`).
- **Registrácia/pozývanie/aktivácia neexistuje**: `signUp`/`createUser`/`inviteUser` → 0 výskytov v `src/`.
- `member_access_codes` je 1:1 viazaná na `auth.users`, nemá stav spotrebovania a jej kód je zároveň heslo (`20261108`: `set_member_access_code` robí `crypt()` do `auth.users.encrypted_password`).
- `user_roles` má PK `(user_id, role_id)` bez `id`; `setUserRole()` robí UPDATE (pre nový účet neúčinné).
- `audit_log` existuje: `action/module/entity_type/entity_id/old_data/new_data`; RLS: SELECT pre admin, INSERT `WITH CHECK (true)`.
- `has_role(uuid,text)` / `has_permission(uuid,text)` existujú a používajú sa v RLS.
- `.env.local` obsahuje len URL + anon key (žiadny service_role).
- `member_access_codes` chýba v `src/types/database.types.ts`.
- Testy: `node --test` unit testy + `supabase/tests/*.sql` + `e2e/dhz-acceptance.spec.ts`.
- **Prepis pozývacieho textu je už overený existujúci vzor** v `src/features/admin/components/AdminMemberManager.tsx` (riadky 226–252): `navigator.share({title,text,url})` s fallbackom na `https://wa.me/?text=${encodeURIComponent(text)}`; text tam znie „DHZ Digital OS – Váš prístupový kód: {code}“ a pod ním je poznámka „Použite WhatsApp, Messenger alebo systémové zdieľanie.“ ⇒ vzor je v aplikácii **už použitý**,Messenger však v ňom **chýba** (iba text v UI, žiadne tlačidlo/deep-link).
- **Route `/register` v repozitári neexistuje** (`src/app/` = `(app)`, `api`, `dashboard`, `login` + root súbory) ⇒ registračná URL sa v zdieľacej správe nedá overiť z kódu; §4.5.2 preto definuje graceful degradation.
- `NEXT_PUBLIC_APP_URL` **nie je** v `.env.local` (iba `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`) ⇒ URL treba odvodiť z `window.location.origin` alebo pridať premennú (O10).

### 9.2 Vyžaduje runtime / DB overenie (v tejto fáze BLOCKED)
- Či sú migrácie v `supabase/migrations/` **skutočne aplikované** v databáze (existencia súboru ≠ aplikovaná migrácia).
- Skutočné definície `roles`, `permissions`, `user_roles`, `audit_log` v bežiacom DB (mohli sa zmeniť mimo repozitára).
- Správanie RLS a `SECURITY DEFINER` funkcií v reálnom DB.
- Konkurenčné správanie `UPDATE ... WHERE consumed_at IS NULL` pod záťažou.
- Správanie `signUp` pri `email_confirmations = true/false` a existujúce auth hooky.
- Obsah `audit_log` triggerov (aby sa raw kód nedostal do logu).
- Existujúce dáta v `member_access_codes` / `user_roles` (duplicity, konzistencia).
- Zapnutý email confirmation flow a custom SMTP v projekte.
- **Reálna registračná URL** v nasadenom prostredí (route `/register` v kóde neexistuje; §4.5.2).
- **Podpora Web Share API** na cieľových zariadeniach (desktop/mobíl) – overiť v reálnom prehliadači, nie simuláciou.
- **Fungovanie `wa.me` deep-linku** (desktop Chrome/Edge/Safari, Android, iOS) – otvorenie okna ≠ odoslanie.
- **Messenger deep-link** – vyžaduje Meta App ID + schválenú `redirect_uri` doménu; bez nich tlačidlo Messenger nebude zobrazené (O8).
- **Reálne správanie `navigator.clipboard`** v produkčnom HTTPS kontexte a fallback `execCommand` v starších prehliadačoch.

**Runtime kroky po schválení:** aplikovať migráciu v neprodukčnom prostredí, spustiť navrhnutý `supabase/tests/k175_invitation_codes_test.sql` (§7.1), overiť `audit_log` bez kódov, a až potom plánovať produkčné nasadenie.
